# 单页形态规范

演示页的目标不是「介绍这个项目」，是让人**在 30 秒内点到真东西**。文字负责补充，界面负责说服。

## 参考基准

ZCode 官网（<https://zcode.z.ai/cn>）是这套形态的现成样板：首屏主视觉不是插图或截图，而是**产品界面的高保真模拟**——真实窗口外壳、真实模块名（任务列表 / 终端 / Git / Goal 面板）、四个仓库分组下带相对时间的任务行、`+734 -7` 的差异计数、可点的分页签与折叠行、带模型选择器的输入区。看完不需要读文案，就已经知道这产品长什么样、怎么用。

抄它的思路，不抄它的行业：把「你的系统最有代表性的那一屏」做到这个密度。

## 五个分区

自上而下，首屏必须落在第 2 项上：

1. **顶部条**（约 56px）：系统名 + 一句话定位 + 右侧「演示数据 · 只读」标记。标记是必需的，避免观众误以为在操作真系统。
2. **Hero：界面复刻**（首屏 60%–75% 高度）——本页主角，细节见下方复刻清单。
3. **功能分区**（3–5 块）：每块 = 一句价值陈述 + 2–3 行说明 + **一个能点的小交互**。纯图文块最多一块，其余必须可交互。
4. **技术栈与实现要点**：这几条同时就是用户建项目卡片时要填的 `stack` 与要点，交付时把建议文案一并给出，让卡片与演示页口径一致。要点写「做了什么决策、解决了什么问题」，不写「使用了 Spring Boot」。
5. **页脚**（一行）：「个人作品演示，数据全部虚构」。

反例：把五块都写成等权重的滚动长文；Hero 用一张静态截图；功能分区堆到 8 块，每块都只有文字。

### 复刻界面怎么嵌进介绍页

别把复刻的应用直接铺满整页——那看着像「打开了一个后台」，而不是「一页作品介绍」。用**设备框**包起来，每个分区嵌一个：

```html
<section class="sec"><div class="wrap">
  <div class="sec-head">
    <span class="pill"><span class="dot"></span>Live Demo · 可交互</span>
    <h2>组工智能助手 · <span class="gt">复刻版</span></h2>
    <p class="sub">这一屏在演什么、怎么点</p>
  </div>
  <div class="hint-chips"><span>① …</span><span>② …</span><span>③ …</span></div>
  <div class="device">
    <div class="chrome">        <!-- 三点 + 地址栏 + 可选的侧栏三态开关 -->
      <div class="cdots"><i></i><i></i><i></i></div>
      <div class="addr">https://<中性域名>/#/index</div>
    </div>
    <div class="screen"><!-- 复刻的应用外壳 --></div>
  </div>
</div></section>
```

- **地址栏用中性域名**，不要写真实内网域名或带项目代号的域名（代号往往就在禁词表里）。
- **侧栏三态**：展开（源项目宽度）/ 收起（源项目 `.hideSidebar` 的宽度，通常 54px）/ 隐藏。主设备给用户一个切换按钮，其余设备统一用收起态——既省纵向空间，又证明收起态也复刻了。
- **一个系统多个操作台**就多放几个小设备（各自带真实路由地址与真实列名），比在一个设备里堆分页签更像「系统全貌」。小设备只保留一行筛选 + 工具条 + 表格即可。

## 保真度分级

| 级别 | 含义 | 判定 |
|---|---|---|
| **L1 骨架保真** | 布局、导航层级、模块名、表格列、状态标签文案、按钮措辞取自真实系统 | 熟悉该系统的人能认出来 |
| **L2 流程保真** | 2–3 个核心流程能真的点完，且含反例路径（校验失败、权限拒绝、终态不可再操作） | 点完能感到「这真是个有约束的系统」 |
| **L3 细节保真** | 空态、加载态、错误文案、快捷键提示、hover 提示 | 挑一处点睛即可 |

**默认交付 L1 + L2**，L3 只做一处。L3 全做会把体积和工时都拖爆，收益却最低。

## Hero 复刻清单

Hero 不是「一张主表截图」，而是**整个应用外壳 + 一个代表性界面**。按这份清单逐项落，缺项就是保真度掉级：

| 元素 | 要求 |
|---|---|
| 外壳 | 侧栏（真实菜单树、真实分组、选中态）+ 顶栏（面包屑、当前用户）+ 页签条；宽高与配色取源项目真值 |
| 多界面 | 系统有两个以上代表性界面时（如 AI 对话页 + 主表操作台），用真实菜单/页签在演示页内切换，别只做一个 |
| 主区 | 真实表格列名 + 筛选条 + 行操作按钮 + 分页器；列数以真实系统为准，别只留三列 |
| 状态标签 | 用真实文案（待审核 / 已通过 / 已驳回 / 在职 / 试用），配色区分语义 |
| 辅助面板 | 分页签或侧栏形式（操作日志 / 详情 / 统计 / 历史会话），至少一个能切 |
| 元数据行 | 源项目若在界面上暴露技术元信息（耗时、命中数、状态码、模型名），照抄——这类细节最能证明是真系统 |
| 数字 | 用 `tabular-nums`，别让表格数字跳动 |

主区选哪一屏：优先「列表 + 筛选 + 行操作」的主表页，它一屏就能交代数据模型、权限、交互三件事；若项目的差异化在别处（AI 对话、看板、编辑器），把那一屏作 Hero，主表页降级为第二个可切换视图。

## 交互写法

- **内存状态机**：一个 `state` 对象 + 一个 `render()`。所有动作只改 `state` 再重画，别在事件里直接改 DOM 文本——后者一多就自相矛盾。
- **动作留痕**：每个动作往「操作日志」推一行（时间 + 动作 + 结果）。这是廉价而有效的保真信号，呼应真实系统的审计表。
- **反例路径是重点**：必填校验失败、无权限被拒、终态不可再操作，各演一个。只有正路可点的演示看着像假的。
- **有限步骤**：每个流程 2–4 步能点完。需要五步以上的流程说明选错了流程。
- **可访问性**：可点的一律用 `<button>`；`:focus-visible` 给可见描边；`@media (prefers-reduced-motion: reduce)` 关掉过渡。
- **刷新即回初值**：这是沙箱限制（不能存储），但对演示是优点——写在页脚提示里即可。

## 假数据

10–20 行足够演示分页、筛选与排序。集中放在文件末尾一个常量里，方便替换与压缩。

人名用通用占位（张三 / 李四 / 王五），部门与公司用中性名（技术部 / 示例科技），日期时间前后自洽，金额与数量量级合理。**不允许从源码或数据库里抄真实记录**——种子数据、测试数据里的真实姓名与单位名同样算泄露。

## 视觉

**有源码或截图时，视觉不是自由项**：把源项目的值抄进 `:root`，别自己挑配色。至少要取真这六类——

1. 主色与语义色（成功 / 警告 / 危险 / 信息），来自主题变量文件而不是组件库默认值；
2. 外壳配色：侧栏背景、子菜单背景、菜单文字与选中态、顶栏背景；
3. 外壳尺寸：侧栏宽度、顶栏高度、页签条高度、内容区 padding；
4. 边框与分隔线色号（表格线常与普通边框不同色）；
5. 字体栈原样照抄（webfont 名保留在 font-family 里但**不外链**，后面接系统字体兜底）；
6. 组件细节：圆角、按钮高度、表头底色、hover 底色。

抄完再自检一遍：截图逐像素采样对比色号，比肉眼可靠（见 `sandbox-contract.md` §8）。

同一套皮肤要贯穿到应用窗口以下的分区，别让「介绍区」和「界面复刻区」像两个产品。

**只有既无源码又无截图时**，才需要自己定风格。可从下面这些风格提示词库里挑一个方向，再落成 CSS：

- <https://www.designprompts.dev> — AI 设计风格浏览器，产出提示词
- <https://motionsites.ai/> — 按分区（hero / SaaS / 作品集 / 电商 / 3D）分类的提示词库 + 动效背景
- <https://www.uiprompt.site/zh/styles> — 风格清单（脚本抓取被 403，需浏览器打开）
- <https://www.stylekit.top/zh> — 同类风格库（抓取时连接中断，需浏览器打开）

动效克制：一次入场 `animation-delay` 阶梯 + hover 微反馈就够；演示页里的花哨动画会抢走对功能的注意力。

## 阶段 B 的确认模板

写码前把下面这张表填好交给用户确认，避免做完再返工：

```text
项目：<系统名>            目标文件：demo-out/<name>.html（默认 runtime 通道，不进仓库）
Hero 复刻对象：<哪一屏>   保真度承诺：L1 + L2（L3 点睛处：<一处>）

分区
  1 顶部条          <系统名 + 一句话定位>
  2 Hero            <侧栏 N 项 / 主表 M 列 / 辅助面板 K 个分页签>
  3 功能分区        <三到五块，各自的价值陈述与内嵌交互>
  4 技术栈与要点    <同时作为项目卡片 stack / 要点的建议文案>
  5 页脚            虚构声明

可点流程
  1 <流程名>：<步骤 1 → 2 → 3>，反例：<校验失败/权限拒绝/终态锁定>
  2 <流程名>：…

  <源码里的身份性名称> → <中性名称>
```
