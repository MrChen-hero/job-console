## 选路线

给了可读的源码目录（可以在仓库外，只读不写）走 A；只有简历文案、文档、截图走 B。两者都有就以 A 为主，A 拿不到的（部署规模、真实用量、团队分工）用 B 补。

## 路线 A：读源码

按顺序走，不要漫游。每步的产出直接对应演示页的某个部位：

| 步 | 抓什么 | 从哪抓 | 进演示页的哪里 |
|---|---|---|---|
| 1 | 系统定位、目标用户、模块划分、领域术语 | `README` / `AGENTS.md` / `docs/` / `docs/specs` | 顶部条一句话定位、分区标题 |
| 2 | 框架、数据库、中间件、特色依赖 | `pom.xml` / `package.json` / `docker-compose*` / `application*.yml` | 技术栈 pills |
| 3 | 模块清单与层级 | Maven 子模块名、前端路由表、菜单表 SQL | Hero 侧栏导航 |
| 4 | 能力清单与权限点 | `@RestController` + `@RequestMapping` 的方法名；权限注解 | 功能分区、权限拒绝的反例路径 |
| 5 | 字段、枚举、状态流转 | 实体类 / `sql/*.ddl` / 常量类 / `status` 字段 | 表格列、状态标签文案、状态机 |
| 6 | 真实界面文案 | 前端 `views/**`、组件里的表格列与表单 | 列名、筛选项、按钮措辞、空态文案 |
| 7 | 差异化能力 | 项目独有的模块（AI、评测、报表、实时推送） | 最值得单独做一块交互的分区 |

好用的检索式（按需替换）：

```text
控制器与接口   @RestController|@Controller|@RequestMapping\(|@(Get|Post|Put|Delete)Mapping
权限点         @PreAuthorize|@RequiresPermissions|hasPermi|hasRole
状态与枚举     enum \w*(Status|State)|STATUS_|_STATE|状态
菜单与路由     insert into sys_menu|sys_role_menu|router/index|createRouter
表格列与表单   el-table-column|a-table-column|el-form-item|label=
词典与常量     sys_dict_data|DictConstants|Constants\.java
```

国内常见的开源后台脚手架二次开发项目，`sys_menu` / `sys_role` / `sys_user` / `sys_dict_data` 这几张表基本能一次性交代模块清单、权限模型与所有下拉选项——优先看它们，比逐个读 Controller 快得多。

**取证预算**：模块清单 + 一屏的完整字段 + 2–3 个状态机就够，控制在十几次读写工具调用内。判定标准是「复刻规格表能填满」，不是「读懂了整个系统」。

## 路线 B：无源码

一次问 2–3 个，别一口气抛八个问题：

1. 这系统给谁用，解决什么问题？一句话。
2. 有哪几类角色？谁看到的东西最不一样？
3. 最能代表这系统的是哪一屏？（引导：通常是「列表 + 筛选 + 行操作」的主表页）
4. 那一屏有哪些列？有哪些筛选项？行上能做什么操作？
5. 有哪些状态？怎么流转？哪个是终态？
6. 技术栈是什么？有没有别人没有的能力？
7. 你最希望面试官看见哪一点？
8. 哪些内容不能出现？（真实单位、客户、人名、上游框架、内网地址）

截图拆解顺序：导航层级 → 表格列名 → 状态标签与配色语义 → 按钮措辞 → 空态与提示文案。

无源码时，凡是问出来或看图推出来的字段，一律进「推断」清单，交付说明里标注，别写成既定事实。

## 复刻规格模板

```text
系统定位    <一句话：给谁解决什么问题>
角色        <角色 A / 角色 B>，差异：<看到的数据范围或功能差异>
Hero 屏     <模块名>
  列        <列 1 / 列 2 / …>（取真实列名）
  筛选      <筛选项>
  行操作    <按钮原文>
  辅助面板  <日志 / 详情 / 统计>
模块清单    <侧栏 5–8 项，改写后的中性名>
状态机      <字段>：<初态> → <终态 A> / <终态 B>，终态不可再流转
反例路径    <校验失败文案> / <权限拒绝场景> / <终态锁定>
真实文案    <按钮、标签、空态的原文摘录>
技术栈      <3–5 个，与 showcase.config.ts 的 stack 对齐>
差异化能力  <最值得单独做一块交互的那个>
改写清单    <源码里的身份性名称> → <中性名称>
证据等级    源码确证：<…>  推断：<…>
```

## 反幻觉三条

1. **文案能抄原文就抄原文**（身份信息除外）。自己编近义词会让熟悉该系统的人一眼看出是假的。
2. **源码里没见过的字段不要出现在演示页**。补齐布局的冲动用留白解决，不用臆造字段。
3. **拿不准的进「推断」清单**，交用户确认再写进页面，别默认自己对。
